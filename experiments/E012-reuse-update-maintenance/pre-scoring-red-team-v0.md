# E012 pre-scoring red team v0

Status: prospective threat analysis before scored model calls.

## Threat 1 — maintenance benchmark accidentally rewards C0

If update documents are unusually explicit summaries, the compiler may receive a cleaner input than realistic source streams.

Containment: update records may state authority and temporal relationship clearly, but answer-critical facts remain distributed across baseline constraint/decision notes and update records. Do not give the compiler a preassembled answer key or future questions.

## Threat 2 — R1 is made artificially hard by irrelevant growth

E012 carries the 32-document E011 large topic forward rather than adding a new distractor explosion. Only four update records are added by W2. R1 therefore receives a strong full-evidence ceiling, not a weak retrieval baseline.

## Threat 3 — C0 rebuild gets unrealistic free routing

Both conditions receive the same deterministic topic boundary. E012 does not claim to measure topic discovery/routing. Routing remains an explicit external-validity limitation.

## Threat 4 — update semantics are ambiguous

If old and new records merely disagree without an explicit authority/time relationship, failure would mix temporal reasoning with underspecified ground truth.

Containment: W1 documents explicitly supersede named W0 current facts. W2 exact-value correction explicitly marks the W1 exact value as erroneous while preserving the W1 constraint update. W2 decision update explicitly supersedes the prior selected option while preserving it as historical.

## Threat 5 — forbidden stale values create substring-scoring artifacts

New current values and revised constraint phrases must not contain prior answer strings as substrings. Deterministic validation must reject collisions before model scoring.

## Threat 6 — full rebuild is an unfairly expensive strawman

Full rebuild is intentionally a conservative maintenance baseline, not a claim that final systems must always rebuild. A negative economic result can show that naive full rebuild does not earn its complexity, but it does **not** prove that all selective/incremental consolidation is impossible.

Therefore E012's kill rule is to narrow/withhold complexity by default, not to declare a theorem that no incremental strategy could ever work.

## Threat 7 — repeated queries are charged multiple model calls

Do not physically rerun identical query bundles N times. Measure one call per condition/wave/query and replay lifecycle economics deterministically for N=1,3,6,10,20.

## Threat 8 — compiler state quality and answer quality are conflated

Report compiled-state preservation/staleness separately from answer outputs. A perfect state with a bad answer is an answer-layer problem; a missing/currently-wrong state is a compilation problem.

## Threat 9 — same-model compiler/answer coupling

The same Luna model builds and consumes C0. This remains a known limitation and possible compatibility advantage. Do not generalize architecture-critical claims without a later changed-model axis.

## Threat 10 — result-dependent parser tolerance

Use GitHub Actions JSONL and extract only the final `assistant.message.data.content`. Pass that content to the unchanged E011 answer parser. Do not add post-result quote/comma/control-character repair. Contract-invalid model content remains invalid.

## Threat 11 — update order leaks query answers through identifiers

Source IDs encode only topic and ordinal source number, not safe/unsafe/current labels. Questions/answers are not included in compiler input. Model call order is fixed before scoring.

## Threat 12 — budget pressure changes the sample

The 400-credit ceiling is an infrastructure stop condition, not a sample-size adaptation. Do not drop topics/waves or change queries because credits are running low. Preserve partial artifacts and resume only the same frozen calls if budget remains available.

## Evidence grade

Even on success, E012 is benchmark evidence for maintenance mechanisms/economics. It is not realistic-workload or production evidence.
